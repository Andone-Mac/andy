同一个国产模型，只改两处引擎参数：16GB 显卡解码 72.8 → 81.6 tok/s

2026-11-09 晚 20:16 到 21:19，一台 16 GB 显卡机器上，同一个国产模型跑了 20 组引擎参数，每组只改一处。留下的只有两处小改动：显存预留 1500→900 MiB、KV 缓存单元 32768→20480。四档提示长度（最长 66,512 词元）的解码中位平均从 72.8 涨到 81.6 tok/s，快 12.2%%；深草稿、CPU 分担预填充、KV 动态增长判负。

一、怎么扫：单变量、同文本三次取中位

跑测在 2026-11-09 晚 20:16:45 至 21:16:34（CST），本机 i7-14700F / 125.6 GiB 内存 / RTX 5080 16 GB，模型是开放权重 Qwen3.8-Flash-Next 的 IQ3_S 档（主权重 54.82 GB 加 28.80 GB PLE 表），引擎为同一份 CUDA 构建，全部跑法由一个驱动脚本串起来：每组生成一份 runtime 配置 → 起独立 systemd 单元 → 探针打三轮 → 停引擎 → 记下显存与内存水位 → 换下一组。全程 20 组、每组冷启动一次引擎、跑测段内共 177 条请求行（当天日志里的请求行还含现网自用流量，不计入）。

探针到第三版才立住：前两版每次换不同文本、单次取样，同一配置两次能差 15%。第三版固定为「每个提示长度先一次冷预填充，再对同一段文本连打三次解码取中位」，文本取自引擎自带的说明文档（自然英文技术文本，去代码块与表格），尾部固定一句「从 1 数到 400，每行一个数」，保证解码长度恒定 256 词元。四档请求目标是 1,024 / 8,192 / 32,768 / 131,072 词元，语料池只凑到 1,320 / 9,169 / 33,269 / 66,512，后文一律按实际词元数写。

所有速度数字由脚本（Tech/1109_agg_iq3s_opt.py）直接解析引擎日志的 serve 行重算，再与探针自己记录的 CSV 对账：共 89 项可比，最大偏差 0.0 tok/s。预填充只取 reused=0 的冷启动行——复用命中时日志那一段只读 5 个词元，速率没有意义。

二、名次：两处「少留显存」的改动赢下 12.2%

赢家不是花哨的参数，是两处「让显存别留那么多余量」的小改动：显存预留从 1500 MiB 降到 900 MiB、KV 缓存单元从 32768 降到 20480。按四档长度的解码中位平均，基线 72.8 tok/s，最优组 81.6 tok/s，快 12.2%；两次复测该组合得 81.6 与 80.0 tok/s。

三、按上下文长度拆开看（解码 tok/s）

增益不在一个长度上均匀分布：短提示（1,320 词元）从 68.2 涨到 77.2，中提示（9,169）基本持平，长提示（33,269 与 66,512）从 70.8 / 75.0 涨到 84.0 / 81.0。这台 16 GB 卡的瓶颈在长上下文，所以这两档才是本轮真正拿到的东西。

四、预填充：只算冷启动（tok/s）

预填充按冷启动口径（reused=0）统计，单位 tok/s。定档配置在 9,169 与 33,269 两档比基线快 9% 与 6%；131,072 档（实际 66,512）基本持平——那一档受内存带宽与 PCIe 限制，显存余量帮不上。

五、为什么快：显存让给专家缓存

为什么少留显存反而快：引擎先把常驻专家表放进内存（两档都固定 52 GiB 预算，实际常驻 45.6–45.8 GiB），再在显存里开一层专家缓存。显存预留是给系统兜底的余量，留 1500 MiB 时这层缓存只有 6.7 GiB；留 900 MiB 时涨到 7.4 GiB，显卡上多放约 367 个专家块，整个跑测期间与内存层交换的次数从 3588 次降到 3194 次，读文件的次数始终是 0 次。

六、噪声底线：同配置两次差 2.0%

同一个配置（预留 900＋KV 20480）在同晚测两次，四档平均分别是 81.6 与 80.0 tok/s，差 2.0%。所以本表里 +4%～+5% 的三项（草稿接受阈值 0.50、常驻重叠、KV 20480 单用）只能算「方向对、幅度存疑」，没有单独复测就不进定档配置；−0.1% 的阈值组算平手。

七、判负的三种想法

旧探针（每长度一次取样）那批只跑了一次就换掉，但三个负结果幅度都在两位数，方向可信：

  • 草稿深度 4→6：平均慢 7.6%，短提示最惨（38 对 48 tok/s）——草稿树越深，被拒的越多，白算的越多。
  • KV 改成动态增长（--kv-grow）：平均慢 8.8%，最长一档从 77.8 掉到 59.9——预分配换成边跑边长，长上下文时反复搬 KV。
  • 工作线程 7→14：平均慢 2.5%。这台机器 20 核 28 线程，解码路径是单线程主导，多开只增调度。
  • 第一批缺基线：只跑完 2 组就中止（20:16–20:21），20:21 起补了带基线的第二批重扫。

八、定档上线与一条副作用

21:20:39 起现网引擎换定档配置：ctx=262144 kv=k8v4/20480 reserve=900 workers=7 budget=52 spec=4/0.70 pcie=0.35 extra='无'。探针之外的第一条真实请求（输出 63 词元）53.2 tok/s，该请求专家缓存命中 58.8%——刚起步、缓存还没热，与跑测期间的稳态不可比。

副作用记一条：启动器等待就绪的上限是 420 秒，IQ3_S 冷加载（读 46.8 GiB 专家＋建常驻表）超过这个上限，启动器在引擎实际就绪前报了 rc=1 退出，实际服务已经起来并可用。待改：把就绪等待按档位分开，IQ3_S 这类大驻留档给到 8–10 分钟。

九、口径与边界

口径与边界：一，全部数字来自本机单次跑测，同一台机器、同一引擎构建、同一份权重；换权重（例如正在准备的 NVFP4 档）需要重扫，参数结论不一定跟着搬。二，解码取中位、按长度分档报告，不给「平均 tok/s」这种掩盖分布的数。三，预填充只统计冷启动行。四，本机的显存预留降到 900 MiB 意味着兜底余量变薄——若同机再跑别的吃显存的进程，需要重新调这个值。五，旧探针批次的单发取样不足以定幅度，只用来定方向。
